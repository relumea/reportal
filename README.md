# reportal

A self-hosted clone of the [RevEng.AI](https://reveng.ai) portal: manage binaries, browse functions, match them across a local corpus, rename with history, and search, all from one local web app.

## Why it exists

The RevEng.AI portal is a hosted service. Reverse-engineering projects that already run locally (rebrew compiles and matches, resembl scores assembly similarity, recoverage visualizes coverage) have no single local place to look at binaries and functions together. reportal is that place. It reads what the sibling engines produce and makes no network call of its own: no account, no hosted upload, no SaaS. There are two opted-in exceptions. The optional AI bridge talks only to the OpenAI-compatible endpoint you configure; leave it unconfigured and reportal makes no model call. Guarded URL ingestion fetches a URL you name, only after you enable it and only through the SSRF guards described under [Knowledge documents](#knowledge-documents); leave it disabled and reportal fetches nothing.

## Install

```bash
uv venv .venv
uv pip install -e ".[dev]" --python .venv/bin/python
# The rebrew engine (`reportal enrich`, the engine routes) is a base dependency,
# installed editable from the sibling ../rebrew checkout by the line above.
# Optional: enable `reportal match` scoring (installs the sibling resembl + rapidfuzz)
uv pip install -e ".[similarity]" --python .venv/bin/python

# Build the web UI (Vite + React + TypeScript, bun). `reportal serve` answers
# 503 ui-not-built until this has produced src/reportal/assets/dist.
cd web && bun install && bun run build
```

## First command

```bash
reportal init
reportal import-rebrew /path/to/rebrew-project
reportal serve
```

`reportal init` writes a `reportal.toml` marker (workspace root) and a `reportal.db` beside it. `reportal import-rebrew` reads the rebrew workspace's `db/coverage.db` and registers its target binaries, analyses and functions; it also ingests the target binary's import stubs as `THUNK` rows, best effort, so the import still succeeds when that engine call fails. `reportal serve` starts the portal on <http://127.0.0.1:8002>.

## Configuration

The AI extras (a function summary, inline comments, type suggestions,
per-function triage and
identifier renames) need
an OpenAI-compatible chat-completions endpoint. reportal is fully usable
without one: every AI route then answers `503 llm-unavailable` and every AI
command exits non-zero.

The same endpoint backs scoped conversations (`reportal chat`, the SPA
Conversations view), which send a bounded prompt built from stored local data
and the recent turns; nothing else about them needs configuration.

Resolution is first match wins per setting: the environment, then the
`[llm]` table of the workspace `reportal.toml`.

| Setting | Env var | `reportal.toml` key | Default |
|---------|---------|---------------------|---------|
| Endpoint | `REPORTAL_LLM_ENDPOINT` | `[llm] endpoint` | none, so AI is disabled |
| API key | `REPORTAL_LLM_API_KEY` | `[llm] api_key` | none, so requests are anonymous |
| Model | `REPORTAL_LLM_MODEL` | `[llm] model` | `gpt-4o-mini` |

```toml
# reportal.toml
[llm]
endpoint = "http://127.0.0.1:11434/v1"
model = "qwen2.5-coder"
```

A request is a JSON POST to `<endpoint>/chat/completions` (the path is not
appended when the endpoint already carries it) with the body
`{"model", "messages", "temperature"}` and `Authorization: Bearer <key>` only
when a key is set. The key is never logged or returned. An endpoint that needs
no key works: a local server accepts anonymous requests.

```bash
reportal decompile 42
reportal summary 42            # store and print the AI summary
reportal ai-comments 42 --json # inline comments as JSON on stdout
reportal suggest-types 42      # parameter/return/local types, with confidence
reportal suggest-renames 42    # clearer names for the unclear identifiers
reportal apply-renames 42 --all   # rewrite the stored decompilation
reportal revert-renames 42     # restore the text the last apply replaced
reportal pipeline 42           # run the AI decompilation pipeline end to end
reportal pipeline-revert 7     # undo what pipeline run 7 wrote
reportal components            # list the components the pipeline composes
reportal components-reload prepare   # re-read one component from its module
reportal components-deactivate prepare   # withdraw a component's contribution
reportal function-triage 1     # score and summarize a binary's top functions
reportal function-triage 1 --limit 3 --function 42
```

### LLM features

`REPORTAL_LLM_ENDPOINT`, `REPORTAL_LLM_API_KEY` and `REPORTAL_LLM_MODEL` (or the
matching `[llm]` keys) enable the decompilation summary, inline comments, type
suggestions, identifier renames, per-function triage, scoped conversations and
the threat report's narrative. Everything else works without them: matching,
lineage, related binaries, composition, detect, the capability, behavior, hardening, secrets,
protocol, crypto, security and remediation scans, and knowledge search all run
with no endpoint configured.

## Knowledge documents

Store text alongside a binary and search it by meaning or by keyword:

```bash
reportal ingest 1 README.md                      # chunk and store a local text file
reportal ingest 1 notes.md --title "Dialog notes"
reportal documents 1                             # list the scope's documents
reportal knowledge 1 "retry counter callback"    # rank the scope's chunks
reportal context 42                              # retrieve what the binary knows about function 42
reportal context 42 --query "dialog timer"       # or ask it a question
reportal ingest-url 1 https://example.com/notes.md --title "Vendor advisory"
reportal ingest-url 1 https://example.com/notes.md --project   # store in the project scope
```

`reportal ingest` reads a text file (markdown, source, config, log, HTML; the suffix must be on the `knowledge.TEXT_EXTENSIONS` allowlist), decodes it as UTF-8, splits it into chunks that overlap at paragraph or sentence boundaries, and stores them in the binary's scope. The same bytes ingested twice in one scope return the stored document instead of a second row, so re-running an ingest is safe. HTML is reduced to its visible text first, binary content is rejected, and a document is capped at `MAX_DOCUMENT_BYTES`, the scope at `MAX_DOCUMENTS_PER_SCOPE` documents and each document at `MAX_CHUNKS_PER_DOCUMENT` chunks.

`reportal knowledge` ranks those chunks against a query. When an embeddings endpoint is configured (see [Configuration](#configuration)) the query is embedded and compared to the stored chunk vectors by cosine similarity; without one the ranking is a local TF-IDF cosine, so search needs no endpoint and no extra dependency. A document ingested on a machine without embeddings stays searchable through the TF-IDF path, and an embeddings request that fails degrades to it rather than failing the ingest.

The same feature is on the HTTP API (`POST /api/binaries/<id>/documents` for a `multipart/form-data` upload, `POST /api/documents` for pasted text, `GET /api/binaries/<id>/documents`, `GET`/`DELETE /api/documents/<id>` and `GET /api/knowledge/search?q=&binary_id=&limit=`) and in the SPA's Knowledge view, which picks a binary, ingests a file or a pasted note and renders the ranked results. By default ingestion reads the bytes you hand it, and the only network call the feature makes is the optional embeddings request.

### Remote URL ingestion

`reportal ingest-url <binary-id> <url> [--title TEXT] [--project]` fetches an HTTP(S) URL and stores its text like any other document. It is **off by default** and must be enabled:

```bash
export REPORTAL_ALLOW_REMOTE_INGEST=1        # or, in reportal.toml:
# [knowledge]
# allow_remote = true
reportal ingest-url 1 https://example.com/notes.md
```

While it is disabled the command exits 1 and `POST /api/knowledge/fetch` answers 403 `remote-ingest-disabled`; `GET /api/knowledge/config` reports `{"allow_remote": false}` and the SPA hides the URL field. Enabling it makes the portal a fetch client, so the target is guarded: only `http`/`https`, a host is required, credentials in the URL are rejected, every address the host resolves to must be public (loopback, private, link-local, multicast, unspecified, reserved and IPv4-mapped IPv6 addresses are refused), and only ports 80 and 443 (plus the scheme default) are accepted. Redirects are followed manually with each hop re-validated, the body is streamed and aborted past `MAX_DOCUMENT_BYTES`, and only `text/*`, `application/json`, `application/xml`, `application/x-yaml` or a missing content type is accepted. No auth header and no cookie is sent. A fetch that fails writes nothing, and the stored `source` is the final URL, so fetching the same content twice dedupes by sha256. One race remains: a DNS answer can change between the check and the connection (TOCTOU). Enable this only when you trust the URLs you will pass it.

The same surface is `GET /api/knowledge/config` and `POST /api/knowledge/fetch` (body `{"scope_kind", "scope_id", "url", "title"}`) on the HTTP API and the destructive `ingest_url` MCP tool. `src/reportal/remote_ingest.py` holds the guards and the test-only `allow_loopback` seam documented in `docs/ARCHITECTURE.md`.

## Retrieval

`reportal context <function-id>` and `GET /api/functions/<id>/knowledge?q=` retrieve the documents most relevant to a function from its binary's scope, and `GET /api/binaries/<id>/knowledge?q=` does the same for a whole binary; the query defaults to the function name and the result list is capped at `knowledge.RETRIEVAL_LIMIT`. Retrieval also feeds the AI features. A conversation appends a bounded `Relevant documents` section (its own binary's documents) to its prompt and returns the hits as `sources`, which the SPA renders as a `Sources` disclosure under the assistant reply; the AI decompilation pipeline's `retrieve-knowledge` stage adds the same context to the summary and type-suggestion prompts, and the read-only `retrieve_knowledge` MCP tool exposes it to clients. Retrieved text is untrusted input: it is quoted as data to reason about, never executed and never treated as an instruction, and the conversation system prompt says so.

The `mentions` row is what a document link looks like: a note that names `FreePrintSetup` and its VA `0x010018a0` is linked to the function it documents.

`reportal graph-build <binary-id>` derives the graph from what reportal already stores: the binary, its functions, the recorded matches, its knowledge documents, the stored struct, capability, unstrip and triage scans and its tags. No LLM, no engine run and no external store is involved, so a rebuild produces the same rows every time and re-running it is safe. `reportal graph <binary-id>` prints the node counts by kind, `--node <id>` prints one node's incoming and outgoing edges grouped by relation, and both add `--json` for scripting. The CLI shows the whole stored graph; the HTTP GET leaves document nodes out unless `?include_documents=true`, so a view stays small.

The node kinds are `binary`, `function`, `document`, `struct`, `tag`, `capability` and `library`; the relations are `contains`, `documented-by`, `has-capability`, `has-tag`, `recovered`, `identifies`, `matched-with` (weight = the recorded similarity) and `mentions`, where a document's text names a function or struct by name or by a `0x` VA literal. Call edges (`function -calls-> function`) are not built: nothing reportal stores carries them, so they are left out rather than guessed. A build is capped by `MAX_GRAPH_NODES` and `MAX_GRAPH_EDGES` and says so rather than growing without bound.

On the HTTP API, `POST /api/binaries/<id>/graph` rebuilds the graph, `GET /api/binaries/<id>/graph` serves it (404 `no-graph` before the first build; `?kind=` keeps one node kind and `?include_documents=true` adds the document nodes, which are off by default) and `GET /api/graph/nodes/<node_id>` returns one node with its neighbors grouped by relation. The SPA's Graph view shows the counts, a filterable node table and the selected node's neighbor groups, with links to the function or document behind a node.

### Optional graph backends

The local graph is the default backend and needs nothing. The graph is pluggable, so it can also be pushed to another store:

```bash
reportal graph-backends                        # list the registered backends
reportal graph-sync 1 --backend sqlite         # report the local graph's counts
reportal graph-query FreePrintSetup            # a node id or a text search
reportal graph-query b1:function:2 --json      # exact node id, as JSON
```

On the HTTP API, `GET /api/graph/backends` lists the registry, `POST /api/binaries/<id>/graph/sync` (body `{"backend": "..."}`, omitted for the configured default) syncs, and `GET /api/graph/query?q=&backend=` queries a backend that supports it; the SPA Graph view carries the backend selector, the Sync control and a query box.

The optional Cognee backend pushes the translated graph into a Cognee dataset. It is off unless the extra is installed:

```bash
uv pip install -e ".[cognee]" --python .venv/bin/python
reportal graph-sync 1 --backend cognee
```

A backend that is registered but not installed answers `503 backend-unavailable` with the install hint instead of a traceback. The dataset name comes from `REPORTAL_COGNEE_DATASET` or, in `reportal.toml`:

```toml
[knowledge]
# graph_backend = "sqlite"       # the backend a sync defaults to
# cognee_dataset = "reportal"    # the dataset the cognee backend writes to
```

Third parties add a backend through the `reportal.graph_backends` entry-point group (`module:attr` naming a `GraphBackend` or a zero-argument factory returning one). The bundled backends are `sqlite` and `cognee`. The translation is tested with a fake backend; the Cognee package itself is optional and its call is not verified against the real library.

## Status

Working:

- Workspace init (`reportal init`), stats, and the web server.
- Binary, analysis, function and match storage in SQLite, with `import-rebrew` ingesting a rebrew `db/coverage.db` plus the target binary's import stubs (`rebrew imports`, stored as `THUNK` rows that never replace a coverage-db function) and `add-binary` registering a binary by sha256. `GET /api/binaries/<id>/download` (`reportal download <binary-id> [--output PATH] [--force]`) streams the stored bytes back as an attachment, reading them in 1 MiB chunks rather than whole (an upload may be up to 256 MiB), naming the file from the sanitized stored name, stating the file's own byte count as `Content-Length` and its suffix-derived content type, and caching indefinitely because the bytes are content-addressed; an unknown id is 404 `binary not found` and a row whose file is gone is 404 `binary not on disk` with the path it looked for. `POST /api/binaries` accepts a browser upload (`multipart/form-data`), stores it under `<workspace>/binaries/<sha256><suffix>`, and dedupes by content hash. The same route takes a batch: repeated `file` parts with a JSON `files` field carrying each file's own name, tags, collection and explicit format/arch, answering one result per file (a duplicate reported as such, a refusal inside that file's entry while the rest register) as one journal action. `reportal extract` and `POST /api/binaries/<id>/extract` unpack a stored archive with the standard library (`.zip`/`.apk`, `.tar`, `.tar.gz`/`.tgz`, `.tar.bz2`, `.tar.xz` and a single-member `.gz`) and register each member as a binary in one collection, refusing a traversal name, an absolute name, a symlink or hardlink, a device or FIFO, or a bomb by ratio or total size per member; `.rar` and `.7z` are refused naming the external unpacker reportal does not ship, firmware unpacking is not implemented, and nothing is ever shelled out.
- Binary fingerprints, imports and strings from the `rebrew` engine: `reportal enrich`, `GET`/`POST /api/binaries/<id>/fingerprint`, and live `/imports` and `/strings` routes. The stored bundle carries md5, sha1, sha256, sha512, the four SHA-3 digests (`sha3_224`, `sha3_256`, `sha3_384`, `sha3_512`), crc32, format, arch, size, imphash, the export hash (SHA-256 over the sorted, lowercased `<ordinal>:<name>` export lines, or over the empty string when the image has no exports) and the per-section entropies; TLSH and ssdeep appear only when their optional backend is installed.
- PE details through `rebrew pe-info`: `reportal pe-info <binary-id>` and `POST /api/binaries/<id>/pe-info` store the identity (format, arch, bits, PE type, image base, entry point, subsystem, timestamp, checksum, size, resource count), the export table (name, absolute VA, ordinal and forwarder target; a forwarded export keeps its record), the section table with each section's entropy, full `IMAGE_SCN_*` characteristic names and read/write/execute flags, the security flags with their summary and raw `dll_characteristics`, the 11-item mitigation checklist with its `N/11` score, the Authenticode state, the debug directory entries, the Rich header, and the presence/counts blocks; `GET /api/binaries/<id>/pe-info` serves the stored result (404 `no-scan` before the first run), and the binary detail view opens with the portal's detail surface: the Binary details identity card, the Hashes card, the Security mitigations card, the Imports and Exports cards, the Sections card, the Code signature card, the Packer detection card and the Unpacked files card. A binary whose format carries no PE metadata answers identity plus a note.
- Bundled file-type, packer and protector detection: `reportal filetype <binary-id>` and `POST /api/binaries/<id>/filetype` assemble the evidence reportal already fetches (the `pe-info` sections and entry point, the `fingerprints` section entropies, the `imports` and the `strings`) and match it against the curated `SIGNATURES` table in `src/reportal/filetypes.py`, covering `packer` (UPX, ASPack, MPRESS, PECompact, NsPack, Petite, tElock, FSG, PKLITE, LZEXE and a high-entropy-executable heuristic), `protector` (Themida/WinLicense, VMProtect, Enigma, Obsidium, Armadillo), `installer` (NSIS, Inno Setup, InstallShield), `runtime` (.NET, Visual Basic, Delphi) and `toolchain` (Microsoft Visual C++, MinGW GCC) signatures. Each signature matches a section-name prefix, an entry-point byte prefix, a string marker, an import DLL name, a Rich header or an executable section at or above an entropy threshold, and confidence is derived from the matched signal kinds: two independent kinds are `high`, a single section name, import or entry-point prefix is `medium`, and a lone string marker or entropy heuristic is `low`. The result is stored as the `filetype` scan; `GET /api/binaries/<id>/filetype` serves the stored result (404 `no-scan` before the first run) and never runs the engine, the binary detail view folds the detection into the Packer detection card (the packer verdict, a peak-section-entropy meter with the packed range marked, the section count, the toolchain compiler string and the match table), and `get_filetype`/`run_filetype` expose the same over MCP. A missing evidence piece is recorded as a note instead of failing the run, and the detection is dependency-free, offline and static (no `diec`, no network call, no execution of the sample). This is a curated subset, not the full DIE database, and a missing signature is not proof a binary is unpacked or unprotected.
- Composed detail reads, the hosted `Binaries` derivations done without an engine call: `reportal die-info <binary-id>` and `GET /api/binaries/<id>/die-info` compose the stored `filetype` and `pe-info` scans and the stored fingerprint into a Detect-It-Easy shaped identity (format, arch, bits, subsystem, entry point, image base) beside the packer, protector, installer, runtime and toolchain matches, each with its confidence, its signals and the fingerprint's section entropies; `reportal additional-details <binary-id> [--status]` and `GET /api/binaries/<id>/additional-details[/status]` report the overlay past the last section (measured from the file against the stored section table), the Rich header's entry count, build and tool ids, the debug entries, the directory presence flags, the counts, the Authenticode summary and the section shape, and which of those inputs are stored at all. Both are stored-only: they run no engine, write nothing and make no network call, and each payload carries a `sources` block naming every input with the command that fills it in, so an empty category reads as a signature miss rather than as an absence. The read-only `get_die_info`, `get_additional_details` and `get_details_status` MCP tools expose the same, and the binary detail view's Detail coverage card renders the coverage report beside the overlay and Rich-header facts no other card shows. The signature table behind the identity is a curated subset of Detect-It-Easy's database, and the payload says so.
- NASM or hex disassembly through `rebrew asm`: `GET /api/functions/<id>/disasm`, resolved with the rebrew project directory `import-rebrew` stored for that binary (NASM listings are cached).
- Basic-block control-flow graph through the same `rebrew asm` verb in its `--format cfg` mode: `GET /api/functions/<id>/cfg` returns the function's blocks (address, byte size, instruction count, first and last instruction text) and the edges between them, with every address an int so the client never parses hex. The graph is derived per request and stores nothing. The payload states the engine's true `block_total` and per-function `block_cap` beside `truncated`, and carries the engine's `note` (or the route's own reason) when it segments nothing; a non-x86 target and a missing engine answer the same 500 `engine-error` and 503 `engine-unavailable` as the other engine routes. The function detail page's code panel toggles between Disassembly and Control flow, and the graph view is an address-ordered block list with a jump control per outgoing edge, back edges labelled and marked. No charting or graph library is involved.
- Memory read, the hosted portal's `read_memory` equivalent: `GET /api/binaries/<id>/memory?va=&length=&kind=` (`reportal memory <binary-id> <address> [--length N] [--offset-kind va|rva|file]`) returns a window of the binary's bytes by absolute virtual address, RVA or raw file offset. The default window is 64 bytes and the cap is 1024, matching the portal; the payload reports the kind it resolved, the address and the bytes as hex. rebrew exposes no raw byte-read command, so the engine surface locates the bytes with its own `rebrew pe-info` section map and reads the file exactly where that map says they live, never parsing a PE in reportal; an address not backed by the image's raw bytes and a window that runs past them are refused (400 `unmapped address`), never fabricated, and a read-only `read_memory` MCP tool exposes the same call. The hosted page's whole-binary hex view is the SPA Memory panel's full-file mode over `GET /api/binaries/<id>/memory/page` (`reportal memory-page <binary-id> [address] [--length N] [--offset-kind va|rva|file]`): a page (default 256 bytes, cap 4096) walks the same section map and answers `bytes` rows and `gap` rows for every byte no section backs, so a region between two sections is a stated gap rather than zero bytes; the mode offers a section select, a go-to taking a virtual address or a file offset, Previous/Next paging, a zero byte dimmed without being hidden, and a byte-range selection copied as hex or a C array.
- Per-section byte coverage, reportal's own metric: `GET /api/binaries/<id>/section-coverage` (`reportal section-coverage <binary-id>`) reads the binary's stored `pe-info` sections and stored functions and reports, per section, the bytes covered, the section size, the percentage and the uncovered count, plus the totals. Overlapping functions are unioned (no double counting) and a function that straddles a section end is clipped to it. A binary with no stored `pe-info` scan answers 404 `no-scan`, and a binary with no stored functions reports `null` percentages with a zero-function note instead of a fabricated 0%. This is reportal's own readout over its stored function table; the hosted portal publishes no equivalent, and the payload says so.
- Decompiled C source through `rebrew decompile`: `reportal decompile <function-id> [--backend kuna] [--named]`, `GET /api/functions/<id>/decompilation` (stored row, else a live compute that is not stored) and `POST /api/functions/<id>/decompilation` (compute and store), using the binary's stored rebrew project context.
- Optional AI extras through an OpenAI-compatible LLM: `reportal summary|ai-comments|suggest-types <function-id>` and `POST /api/functions/<id>/summary|ai-comments|type-suggestions` feed the stored decompilation to the configured endpoint and keep the result in the `ai_artifacts` table. The matching `GET`s are stored-only (404 `no-artifact`) and never call a model. No endpoint configured means every AI route answers 503 `llm-unavailable` and every AI command exits non-zero, and the model's input is always a decompilation you already stored. The inline-comments artifact is served at `/ai-comments` because the analyst comment routes own `/comments`. See [Configuration](#configuration).
- Optional AI identifier renaming: `reportal suggest-renames <function-id>` asks the same endpoint for clearer names for the unclear identifiers (variables, parameters, functions, globals) of the **stored** decompilation and keeps them under the `renames` artifact; entries whose `from` is not in the source are dropped. `reportal apply-renames <function-id> [--all|--from NAME --to NAME] [--rename-function]` rewrites whole-token occurrences outside string literals, refusing C keywords and identifiers shorter than `renames.MIN_IDENTIFIER_LENGTH`, journals the previous text, and `reportal revert-renames <function-id>` restores it. `--rename-function` also renames the function row, recorded in `name_history` with source `renames`. The matching routes are `POST`/`GET /api/functions/<id>/renames` and `POST /api/functions/<id>/renames/apply|revert`; the apply is deterministic text work and needs no endpoint.
- Scoped agent conversations, local and optional: `reportal chat-new --function <id> | --binary <id>` opens a chat over a stored function or binary, `reportal chat <conversation-id> "message"` sends one turn and prints the reply, and `reportal conversations` lists them. The request is a fixed system instruction plus a bounded context assembled from stored local data only (the function row with its stored disassembly and decompilation, or the binary row with its stored triage summary and capabilities) and the last `HISTORY_TURN_LIMIT` turns; no engine runs and no tool is called. Turns live in the `conversations`/`messages` tables (`GET`/`POST /api/conversations`, `GET`/`DELETE /api/conversations/<id>`, `POST /api/conversations/<id>/messages`), the SPA Conversations view lists, creates, opens, sends and deletes threads, and both detail views carry a Chat about this action. This is not the hosted portal's tool-calling agent, and it is off until the same endpoint as the AI extras is configured.
- Cross-references through `rebrew xrefs`: `reportal xrefs <function-id> [--kind NAME]...` and `GET /api/functions/<id>/xrefs?kind=...` list the references to a function live through its binary's rebrew project context. `reportal references <function-id>` and `GET /api/functions/<id>/references` add the hosted function page's three reference tables from `rebrew describe <hex-va> --json` in that same context: Globals (the data addresses the function reads, writes or loads, each with the access the instruction makes clear and the section the stored `pe-info` scan places it in), Callers (one row per call site into the function) and Callees (the calls it makes, an import-slot call with no resolved name reported as indirect).
- Recovered struct definitions through `rebrew recover-structs`: `reportal structs <binary-id> [--decompiler kuna] [--limit N]` and `POST /api/binaries/<id>/structs` store the engine result as the `structs` scan, and `GET /api/binaries/<id>/structs` serves it back (404 `no-scan` before the first run).
- Editable data types over that recovery: `POST /api/binaries/<id>/data-types/import` (`reportal types-import <binary-id>`) parses each stored definition into a local model that keeps its declaration kind (`struct`, `union`, `enum`, `typedef`, `pointer`, `array`, `function`; members with running offsets and derived sizes, a union's members all at offset 0, an enum's named values, a typedef/pointer/array/function target, and a bitfield member's width; an unknown type becomes size 0 with a note, and a definition that matches no shape is skipped with a reason), `GET /api/binaries/<id>/data-types` (`reportal types <binary-id>`) serves it with each type's kind, namespace, size and padded As-C declaration, takes optional `kind`/`namespace`/`search` filters and answers a namespace tree, `GET /api/data-types/<id>/references` serves the two reverse indices (what references the type, and which stored function signatures name it, both matched by name), `PATCH`/`DELETE /api/data-types/<id>` and the `members` routes (`reportal type-rename`, `type-kind`, `type-namespace`, `type-size`, `type-member`, `type-member-add`, `type-member-gap`, `type-member-ungap`) rename a type, set its kind, namespace or declared size, rename/retype a member or set its bit width, add a member (appended or at a position: `index` is where it goes and `after` names the member it follows, refused together), convert a member to explicit padding (`char gap_XXXX[N]`, the recovered convention) and back, remove a member or delete a type, and every edit recomputes offsets and the total size, rejecting a bad identifier or a duplicate member. `POST`/`PATCH`/`DELETE /api/data-types/<id>/values[/<value>]` (`reportal type-value-add`, `type-value-edit`, `type-value-remove`) add, rename/revalue and remove an enum constant, taking a value as an integer or a decimal/`0x` literal, echoing both, continuing from the last constant when none is given and saying so, and refusing a duplicate name or value. Every type payload also carries a `size_check` naming both numbers when the declared size and the members' extent disagree; the check is read-only. Every one of those mutations records the state it replaced and the state it wrote, so `GET /api/data-types/<id>/history` (`reportal types-history <type-id>`) lists the type's versions newest first with each version's per-field diff (name, kind, namespace, size, members, enum values, target, element count) and `POST /api/data-types/<id>/history/<history_id>/revert` (`reportal types-revert <type-id> <history-id>`) restores exactly one recorded version, journaling both the row it replaces and the history row it appends so the revert can itself be undone (a second revert of the same row is a no-op, an unknown row is 404 `history not found`). The history rows are keyed by the type id and do not cascade with the row, so a deleted type's history stays readable and its revert puts the row back under its original id (a name another row now holds is refused `duplicate name`). `POST /api/binaries/<id>/data-types/export` (`reportal types-export <binary-id> <path> [--force]`) is the apply step: it renders the model as one deterministic `#pragma once` C header at the explicit path, refuses an existing target without `force` (409 `export-exists`) and never writes into the rebrew project or a workspace location the caller did not name.

- Editable function signatures over the stored decompilations: `POST /api/binaries/<id>/signatures/import` (`reportal signatures-import <binary-id>`) parses the declaration line of every stored decompilation (`unsigned int sub_1005640(unsigned int a0, ...)`, a `__stdcall`/`__cdecl`/`__fastcall` keyword, pointer returns, arrays and unnamed parameters) into a local model and reports created/updated/skipped counts with a reason per decompilation that does not parse; `GET /api/binaries/<id>/signatures` (`reportal signatures <binary-id>`) lists the model. `GET /api/functions/<id>/signature` (`reportal signature <function-id>`) returns the signature and its rendered prototype, `PATCH /api/functions/<id>/signature` (`reportal signature-set <function-id> [--return-type T] [--convention C]`) sets the return type or calling convention, the `parameters` routes (`reportal signature-param`, `signature-param-add`, `signature-param-rm`) edit, add at an index or append, and remove an ordered parameter (indices stay contiguous), and `DELETE /api/functions/<id>/signature` deletes one. Edits validate a C identifier, reject an empty type or duplicate parameter name and reject an out-of-range index. Every mutation records the state it replaced: `GET /api/functions/<id>/signature/history` (`reportal signature-history <function-id>`) lists it newest first, and `POST /api/functions/<id>/signature/history/<history_id>/revert` (`reportal signature-revert <function-id> <history-id>`) restores exactly that state, journaling both the row it replaces and the history row it appends so the revert can itself be undone (a second revert of the same row is a no-op, an unknown row is 404 `history not found`). `POST /api/binaries/<id>/signatures/export` (`reportal signatures-export <binary-id> <path> [--force]`) renders the model as one deterministic `#pragma once` prototype header ordered by function name, with the same atomic write, `force` and parent-directory rules as the type header. A parameter also carries the optional `at` (where the target convention passes the argument: a register like `ecx` or a stack slot like `[esp+4]`), `kind` (`value`, `pointer`, `array` or `struct`) and `bits` (its width), editable through `reportal signature-param <function-id> <index> [--at SLOT] [--kind K] [--bits N] [--clear FIELD]` and the panel; an absent field stays null (the payload offers the convention-implied location as `default_at`, never as `at`), the rendered prototype annotates only the fields it has, and `reportal signature-param-move <function-id> <index> <to-index>` (the `parameters/<index>/move` POST) reorders a parameter while recomputing the arrival locations the calling convention implies.
- Crypto scan through `rebrew crypto-scan`: `reportal crypto-scan <binary-id>` and `POST /api/binaries/<id>/crypto-scan` detect crypto constants (AES S-box and inverse, SHA-256 K/H) and known crypto APIs, and `GET /api/binaries/<id>/crypto-scan` serves the stored result (404 `no-scan` before the first run).
- Capability tagging, locally and deterministically: `reportal capabilities <binary-id>` and `POST /api/binaries/<id>/capabilities` run `rebrew imports` and `rebrew strings` and match them against a fixed rule table (networking, crypto, file-io, registry, process-execution, threading, memory, dynamic-loading, anti-debug, persistence, synchronization, compression, ui, console), storing the categories as the `capabilities` scan with `high` confidence for import evidence and `medium` for string-only evidence; `GET /api/binaries/<id>/capabilities` serves the stored result (404 `no-scan` before the first run). This is not the hosted portal's LLM agent: no model, no network call.
- Detect, local family matching against a curated signature store: `reportal family-add <reference-binary-id> <name> [--alias TEXT]... [--notes TEXT]` registers a malware family from a reference binary, `reportal families` lists the store, `reportal family-rm <family-id>` deletes one and `reportal detect <binary-id>` matches a binary against it; `GET`/`POST /api/families`, `GET`/`DELETE /api/families/<id>` and `POST`/`GET /api/binaries/<id>/detect` expose the same store over HTTP, and the MCP tools `list_families`, `get_detect_scan`, `register_family`, `delete_family` and `run_detect` expose it over stdio. reportal bundles no external threat-intelligence feed and cannot, so the analyst curates the families: registration derives the reference binary's signature bundle once (the engine fingerprint's `sha256`, `imphash` and `rich_header_hash`, an import hash computed locally as the sha256 of the sorted lowercased `dll:name` entries, the canonical import-name set and the capability set from `capabilities.classify`) and stores it with the family. Detection scores the target's bundle against every family and reports each matched signal with its confidence: exact `sha256` is `high` `exact-binary`, exact `imphash` `high` `import-fingerprint`, exact `rich_header_hash` `medium` `toolchain-fingerprint`, exact import hash `high` `import-set`, an import-name Jaccard ratio at or above 0.8 `medium` `import-overlap`, and a capability-set Jaccard ratio at or above 0.8 `low` `capability-overlap`. A family's confidence is its strongest signal, the payload carries the scope and both thresholds in its notes, and matching nothing is a valid result. The detection is stored as the `detect` scan and served by its stored-only `GET` without an engine. The hosted portal's Detect runs against its own curated families and models and is coming soon upstream; this is the local, offline equivalent, not the same data.
- Protocol inference, locally and deterministically: `reportal protocols <binary-id>` and `POST /api/binaries/<id>/protocols` run `rebrew imports` and `rebrew strings` (both standalone) and name the network protocols a binary speaks from the fixed table in `src/reportal/protocols.py`, storing the result as the `protocols` scan; `GET /api/binaries/<id>/protocols` serves the stored result (404 `no-scan` before the first run). Each entry names a protocol family (`http`, `https`, `tls`, `dns`, `ftp`, `smtp`, `imap`, `pop3`, `irc`, `telnet`, `ssh`, `smb`, `rdp`, `ldap`, `snmp`, `ntp`, `quic`, `mqtt`, `websocket`, `tcp`, `udp`) with a confidence, the evidence that named it (`import`, `scheme` or `string`) and its well-known ports. A dedicated API (`WinHttpSendRequest`, `ldap_bind`) or a `scheme://` literal is `high`, the generic socket family on `tcp`/`udp` or a protocol literal (`HTTP/1.1`, `EHLO`, `SSH-2.0`) is `medium`, and a protocol with both an import match and a scheme or literal match is promoted to `high`. A port is evidence only when the same string also carries a host or URL, so a lone `80` or `443` constant names nothing. This goes beyond the networking behavior domain by naming concrete families, and it is not the hosted portal's model: no LLM and no network call. Inference is not proof of use, since an import means the API can be called and a literal means the text is present. The binary detail view carries a Protocols panel that loads the stored scan and runs it on demand.
- Behavior scans, locally and deterministically: `reportal behavior <binary-id> <domain>` (or `--all`) and `POST /api/binaries/<id>/behavior/<domain>` match the binary's imports and strings (`rebrew imports` and `rebrew strings`, both standalone) against a fixed rule table per domain in `src/reportal/behavior.py` and store each as its own `execution`, `networking` or `filesystem` scan, with `high` confidence for import evidence and `medium` for string-only evidence. `GET /api/binaries/<id>/behavior` serves all three stored scans (null where absent) and `GET /api/binaries/<id>/behavior/<domain>` serves one (404 `no-scan` before the first run). This is not the hosted portal's execution/networking/filesystem agents: no model, no network call of its own and no execution of the binary. The binary detail view carries a Behavior panel with a domain select.
- Hardening scans, locally and deterministically: `reportal hardening <binary-id> <domain>` (or `--all`) and `POST /api/binaries/<id>/hardening/<domain>` cover two domains from `src/reportal/hardening.py`. `anti-analysis` matches the imports and strings against a fixed rule table (`anti-debug-api`, `timing-check`, `vm-or-sandbox-artifact`, `exception-tampering`, `debugger-detection-string`) with `high` confidence for import evidence and `medium` for string-only evidence. `obfuscation` applies named thresholds over the engine's fingerprint, imports and strings plus the stored triage dossier: a code-like section at or above 7.0 entropy, a size-weighted mean section entropy at or above 6.8, a sparse import or string table for a binary at or above 64 KiB, and packer/protector names or section conventions (`UPX0`, `.aspack`, `.themida`), reporting a `packer_likelihood` of `high` (three findings), `medium` (two) or `low`. `GET /api/binaries/<id>/hardening` serves both stored scans (null where absent) and `GET /api/binaries/<id>/hardening/<domain>` serves one (404 `no-scan` before the first run). A missing fingerprint is recorded as a note with the entropy thresholds skipped instead of failing the scan. A missing finding is not proof the binary is unprotected, and a firing heuristic is not proof of a packer; these are static heuristics with no model, no network call and no execution of the binary. The binary detail view carries a Hardening panel with a domain select and the packer likelihood.
- Secrets scan, locally and deterministically: `reportal secrets <binary-id>` and `POST /api/binaries/<id>/secrets` read `rebrew strings` (standalone, no project context) and match the entries against a fixed pattern table in `src/reportal/secrets.py` (AWS access key id and context-anchored secret access key, Google API key, GitHub `gh[pousr]_` token, Slack `xox[baprs]-` token, Stripe live/test key, OpenAI-style `sk-` key, JWT, PEM private key header, a database connection string carrying `Password=`/`Pwd=`, and a generic quoted assignment to a credential-named field) plus a Shannon-entropy check for key-sized blobs. Findings are stored as the `secrets` scan; `GET /api/binaries/<id>/secrets` serves the stored result (404 `no-scan` before the first run). Each finding carries the raw value and a redacted form, and the values are sensitive because they are stored locally; human output warns and shows the redacted value, and the binary detail Secrets panel reveals one row at a time. This is not the hosted portal's secret-recovery model: no LLM and no network call.
- Security scan through `rebrew security-scan`: `reportal security-scan <binary-id> [--min-severity high|medium|low]` and `POST /api/binaries/<id>/security-scan` run the local rule-based scan over the binary's rebrew reversed C sources (unbounded copy, format string, command execution, unchecked memcpy, insecure random, stack allocation) and store the findings as the `security` scan; `GET /api/binaries/<id>/security-scan` serves the stored result (404 `no-scan` before the first run).
- Threat report, locally and deterministically: `reportal threat <binary-id> [--narrative]` and `POST /api/binaries/<id>/threat` run `rebrew strings` and `rebrew imports` (both standalone), extract indicators of compromise with the fixed rules in `src/reportal/threat.py` (urls, domains, ipv4, emails, registry paths, file paths and md5/sha1/sha256 hashes; private and loopback addresses are kept and flagged rather than dropped), map them together with the stored capability scan onto a curated MITRE ATT&CK table, and store the result as the `threat` scan with each technique's evidence and a `high`/`medium` confidence; `GET /api/binaries/<id>/threat` serves the stored report (404 `no-scan` before the first run). `--narrative` adds a short analyst summary from the configured OpenAI-compatible endpoint, with the IOCs and techniques passed as untrusted context, and without an endpoint the report is still returned with the reason recorded. No external threat-intelligence service is contacted, and this is not the hosted portal's model-driven report. The binary detail view carries a Threat report panel that loads the stored report and runs it on demand, and the Triage panel renders the same verdict. Every threat and triage response adds a software-type badge and an analysis-level 0-100 threat score, both derived at read time from the scans reportal already stores (`threat.classify_binary`). The software type comes from a closed vocabulary (`ransomware`, `keylogger`, `coinminer`, `downloader`, `installer`, `managed-application`, `packed-executable`) matched over the stored file-type detection, capability tags, ATT&CK techniques and triage string and DLL samples, with the signals that fired and a confidence derived from how many independent signal kinds matched; the score names every contribution (packing, capabilities, indicators, techniques) and the points it added, renders as a meter with the unlit remainder and a fixed readout, and answers `null` with the reason rather than a zero when nothing carries evidence. Both are reportal's own heuristics, said so in the payload: the hosted portal's score comes from a model reportal does not run, and the vocabulary deliberately omits Trojan, Backdoor, Spyware and Worm, which static evidence cannot name honestly.
- Remediation artifacts, locally and deterministically: `reportal yara <binary-id> [--output PATH]`, `reportal snort <binary-id> [--output PATH]` and `reportal stix <binary-id> [--output PATH]` back `POST /api/binaries/<id>/remediation`, which reads `rebrew strings` and `rebrew imports` (and `rebrew fingerprints` when no fingerprint is stored) for the YARA rule, picks bounded sets of distinctive literals (data strings and import API names) with the fixed denylist rules in `src/reportal/remediation.py`, and renders one complete rule (sanitized name; meta with author, date, binary name, sha256, imphash and Rich-header hash; hex-escaped `$sN` and `$iN` entries with wide literals as `ascii wide`; a single condition that anchors on `pe.imphash()` for a PE with one and otherwise on the file magic, bounds the filesize and clamps each match count). The payload reports `string_count`, `import_count` and a `specificity` grade (`high`/`medium`/`low`), and carries two further artifacts built from the stored `threat` scan (read, never re-run): a Snort 2 rule set (one `alert tcp $HOME_NET any -> $EXTERNAL_NET <port>` rule per URL, domain and IPv4 indicator, ordered by family then value, the port from the indicator or the stored `protocols` scan, SIDs counting up from 1000000, and an honest empty result with a note when no network indicator exists) and a deterministic STIX 2.1 bundle (a reportal `identity`, one `indicator` per URL, domain, IPv4, email and hash IOC with a `stix` pattern, `created`/`modified`/`valid_from` from the date, and `uuid5`-derived ids). The rule is compiled with `yarac` when it is installed and all three artifacts are stored as the `remediation` scan; without `yarac` the rule is stored with `validated: false` and `validator: null` instead of failing, so the requirement is optional. `GET /api/binaries/<id>/remediation` serves the stored payload (404 `no-scan` before the first run), `GET /api/binaries/<id>/remediation/<yara\|snort\|stix>` serves one artifact as text or JSON (404 `no-artifact` when the stored payload lacks it), `--output` writes the selected artifact atomically to a path, and the binary detail view carries a Remediation panel with a Generate control and a collapsible section per artifact, each with a copy control or an empty state. The Snort rule is a basic content rule and the STIX bundle a minimal export, neither schema-validated against an external validator.
- Auto-unstrip through `rebrew identify-library --dry-run`: `reportal unstrip <binary-id> [--min-confidence F]` and `POST /api/binaries/<id>/unstrip` join the engine's library candidates (FLIRT, CRT and IAT import matches) to the stored functions and record rename proposals as the `unstrip` scan without renaming anything; `reportal unstrip-apply <function-id> [--name TEXT]` and `POST /api/binaries/<id>/unstrip/apply` apply one stored proposal with source `unstrip`. A user-authored function name is never proposed for overwrite.
- Local function matching: `reportal match <binary-id>` and `POST /api/binaries/<id>/match` rank every function against the candidate corpus with a structural similarity score and softmax confidence, under the Match Settings scope (`--min-similarity`, `--min-confidence`, `--top`, `--self`/`--no-self`, `--platform`, `--arch`, `--binary`, `--collection`), where every setting defaults to the unscoped run and is refused outside its bound or closed vocabulary. The platform/architecture scope is a coarse filter over a binary's stored fingerprint (else its suffix-derived format/arch columns), not a guarantee, and the response says so. The run records the settings it used on every row it writes, so `GET /api/binaries/<id>/matches` (stored-only) reports them back with the derived `difference` (`100 - similarity`) and the quality `band` beside the stored similarity and confidence. Requires the optional `similarity` extra (`uv sync --extra similarity`).
- Match / Diff and symbol transfer: the SPA's `#/matches` view lists a binary's recorded edges ranked by a Similarity / Confidence / Difference toggle with a stacked quality bar over the five bands, carries the Match Settings sheet with a removable chip per active setting, and offers a per-row transfer-mode selector and a Bulk Transfer dialog with per-row Names/Signature checkboxes. `reportal apply-match <function-id> <candidate-function-id> [--mode name|signature|both]` and `POST /api/functions/<id>/apply-match` transfer a candidate's name, its signature, or both; a signature transfer copies the return type, calling convention and parameters, reports any referenced local type the target's binary has no definition for instead of dropping it, and refuses a target whose non-empty calling convention differs with 409 `signature-conflict`. `POST /api/binaries/<id>/matches/transfer` applies a list of `(function, candidate, mode)` rows as one journaled action with a per-row applied/skipped/failed report; one row's failure keeps the rows that succeeded, and `dry_run` previews without writing.
- Function diff view: `reportal diff <function-id> <candidate-function-id> [--kind disasm|decomp] [--no-normalize]` and `GET /api/functions/<id>/diff/<candidate_id>?kind=&normalize=` align a function against a match candidate side by side, marking the changed lines and reporting the per-operation counts and the match similarity. A `disasm` side is the cache-backed `rebrew asm` listing, a `decomp` side the stored decompilation or a live unstored `rebrew decompile`; normalization strips addresses, encoded bytes and comments before comparing. The route requires a recorded match for an explicit candidate (400 `no-such-match`), and without one it aligns against the function's best recorded match. The function detail Matches panel and the `#/matches` view carry a per-row Compare action to `#/diff/<function-id>/<candidate-id>`, and `diff_functions` exposes the same alignment as an MCP tool.
- Lineage, pairwise and deterministic: `reportal lineage <left-binary-id> <right-binary-id> [--no-refine]` and `POST /api/binaries/<id>/lineage` (body `{"other_binary_id": N, "refine": true}`) compare two binaries' stored function lists and classify every function as `unchanged`, `changed`, `added` or `removed`. Exact names pair first, preferring the closest size (same size is unchanged, a different size changed); the unnamed/placeholder names (`sub_*`, `fcn_*`, `FUNC_*`, empty) pair inside a 10% size bucket with the structural similarity the optional `similarity` extra scores over cached `rebrew asm` listings (at or above 95 unchanged, at or above 70 changed). Without the extra, or with `refine: false`, only the name/size pass runs and the payload records `refined: false` instead of failing. The payload carries the exact status counts, `matched_percent` (the paired share of both sides) and rows sorted by status then VA, capped at 500 rows while the counts stay exact. `GET /api/binaries/<id>/lineage?other_binary_id=N` serves the stored comparison (404 `no-scan` before the first run) and the same route without the query lists every comparison stored for the binary; one comparison is kept per pair, so a re-run refreshes that pair. The binary detail Lineage panel picks another binary, runs the comparison and renders the counts with per-status tables linked to the functions, and `get_lineage`/`run_lineage` expose the same over MCP. This is not the hosted portal's agent-based version investigation: it is a local pairing of stored functions with no model and no network call.
- Related binaries, ranked deterministically: `reportal related <binary-id> [--limit N] [--all]` and `POST /api/binaries/<id>/related` (body optional `{"limit": N, "include_unrelated": bool}`) rank every other stored binary against the target using the data reportal already holds. An identical `sha256` is `identical`, an identical `imphash` `same-imports`, an identical Rich-header hash `same-toolchain`, an import-name Jaccard ratio at or above 0.8 `similar-lifecycle`, a capability-set Jaccard ratio at or above 0.8 `similar-capabilities`, and, only when nothing stronger matched, the same format/arch with a size within 10% `similar-size`; a candidate that matches nothing is `unrelated` and is left out unless `--all` (or `include_unrelated`) is given. The target bundle is the stored fingerprint when one exists, else the engine's; imports and strings come from the engine when it is available and from the stored fingerprint and capability scan otherwise, so a missing engine degrades with a note instead of failing. Rows are sorted by classification rank, then similarity, then name and capped at `limit` (default 20), the payload reports the exact number of candidates considered and notes each binary skipped for having no file on disk, and the ranking is stored as the `related` scan (served stored-only by `GET /api/binaries/<id>/related`, 404 `no-scan` before the first run). The binary detail view carries a Related binaries panel, and `get_related_binaries`/`run_related_binaries` expose the same over MCP. This is a local ranking over hashes, imports, capabilities and size; the hosted portal compares against its own corpus.
- Composition analysis, the portal's per-binary block: `reportal composition <binary-id> [--json]` and `POST`/`GET /api/binaries/<id>/composition` read the binary's stored functions and the `matches` table alone (no matching run and no engine) and report the headline `Matched: N / M (P%)` where N is the functions with at least one stored match against another binary, the five function-name-source buckets (`System`, `Auto Unstrip`, `AI Agent`, `User`, `No Debug Info`) mapped onto reportal's stored `name_source` vocabulary (a placeholder or empty name is `No Debug Info`, `import` and `rebrew` are `System`, `unstrip` is `Auto Unstrip`, `renames` and any `ai*` source are `AI Agent`, and anything else is `User`), the five match-quality bands (`Strong Match` at or above 95, `Match` at or above 80, `Partial Match` at or above 70, `Weak Match` below, and `No Match` for a function with no stored match row), one row per other binary the functions matched to (name, sha256, count and percent of the binary's total functions, sorted by count descending then binary id) and one row per function with its best match's similarity and the matched binary's name, or an explicit `No match`. The band cutoffs are reportal's own named constants aligned with `lineage.UNCHANGED_THRESHOLD`, `matching.DEFAULT_MIN_SIMILARITY` and `lineage.CHANGED_THRESHOLD`; the hosted portal publishes none. The payload is stored as the `composition` scan (the `GET` is stored-only and answers 404 `no-scan` before the first run, and the panel carries a Run analysis control), and `get_composition`/`run_composition` expose the same over MCP. A store with no match rows still succeeds with `refined: false` and a note naming `reportal match <binary-id>`; a stored match whose candidate is in the same binary is not a composition and is reported in the notes.
- Triage and reports from the `rebrew` engine: `reportal triage <binary-id>` stores the one-shot dossier, and `reportal report <binary-id>` writes the HTML site into the workspace `reports/<binary-id>/` tree and stores the coverage summary. `POST /api/binaries/<id>/triage` and `/report` compute and store; the matching `GET`s serve the stored result and answer 404 `no-scan` before the first run, and the generated site is browsable at `/reports/<binary-id>/`.
- PDF summary report: `reportal report-pdf <binary-id> [--output PATH] [--force]` renders a text-only PDF from the scans the portal already stored (title block, coverage, fingerprint, capabilities, triage, function triage, security, crypto, threat, secrets counts, behavior, protocols, hardening, remediation and lineage) and writes it to `<workspace>/reports/<binary-id>/report.pdf` by default, or elsewhere with `--output`. `POST /api/binaries/<id>/report/pdf` generates it and `GET /api/binaries/<id>/report/pdf` serves it as `application/pdf` (404 `no-pdf` before the first render); the binary detail Report panel carries Download PDF and Generate PDF controls. The generator is stdlib-only, the streams are uncompressed, and the output is deterministic for the same stored rows and generated date.
- Per-function triage, the per-function half of that surface: `reportal function-triage <binary-id> [--limit N] [--function ID]...` and `POST /api/binaries/<id>/function-triage` (body `{"function_ids": [...], "limit": N}`, both optional) select the target functions (explicit ids, else the top `limit` candidates), build each one's untrusted context (its stored decompilation, else a `rebrew asm` disassembly), and ask the configured endpoint for a `{"summary", "score" 0..1, "capabilities"}` answer, storing one `function-triage` artifact per function plus the aggregate scan; `GET /api/binaries/<id>/function-triage` serves the stored result (404 `no-scan` before the first run). Without an endpoint it degrades cleanly: `function_triage.score_candidates` ranks size, a non-matching status, a stored decompilation, a placeholder name and the recorded match count into a named `heuristic_score` in 0..1 with its reasons, and each row keeps that score with a deterministic one-line summary built from the function's metadata, `model: ""` and a note saying so. A function whose context cannot be resolved is listed under `skipped` with a reason rather than failing the run, and a missing engine is 503 only when the LLM path needs a disassembly. The binary detail view carries a Function triage panel with a limit input, the scored table with each row's method badge and the skipped list.
- Bulk data types and signatures: `reportal signature-copy <analysis-id> <source-id> <target-id>...`, `data-types-import <analysis-id> [--definition DECL]... [--file PATH] [--update-only]`, `signatures-batch <function-id>...` and `data-type-functions <analysis-id> <data-type-id>`, the `POST /api/analyses/<id>/signatures/copy`, `POST|PUT /api/analyses/<id>/data-types`, `GET /api/functions/signatures?ids=` and `GET /api/analyses/<id>/data-types/<type_id>/functions` routes, the `copy_signature`, `import_type_definitions`, `get_signature_batch` and `get_data_type_functions` MCP tools, and the signature panel's copy control with the data types panel's declaration box. A signature copy writes the return type, calling convention and parameters onto each target (creating the row a target needed); a data-type import parses each declaration with the same parser the structs scan import uses and splits a whole header at top-level semicolons, so a struct may span lines; the batch read answers in the caller's order with `null` for a function that has none. Every bulk write is one journaled action, so a revert deletes what a create added and restores what an update replaced.
- Regular-expression and multi-value search: `reportal search <query> [--kind K] [--limit N] [--regex]` (or `GET /api/search?q=&kind=&regex=true`) matches a substring by default and a **bounded regular expression** with `--regex`: the pattern is capped at `store.MAX_REGEX_CHARS`, its compiled form is cached (`REGEX_CACHE_SIZE`), a pattern that does not compile answers 400 `invalid regex`, and the `sha256` kind refuses a pattern because a hash prefix is a literal by definition. The match runs in SQL through a `REGEXP` function registered on the connection (standard SQLite ships no engine of its own), so a pattern never turns into a full scan into Python. The function list's string filter takes several needles at once, combined as any-of (`GET /api/binaries/<id>/functions?string=a&string=b`, at most `api.MAX_FUNCTION_STRINGS` values), each with its own Remove chip in the SPA, and the same `regex=true` flag turns them into patterns. The `search` and `list_functions` MCP tools expose both. One ceiling is stated rather than hidden: Python's `re` cannot be interrupted once a match is running, so the pattern's length is what is bounded, not its running time.
- Type provenance and list controls: every stored data type carries a `source` (the structs scan, a manual create, a bulk declaration, the debug-symbol import or the AI bridge), and `data_types.source_label` maps it onto the portal's four labels (`System`, `User`, `Auto Unstrip`, `AI`) through one explicit table: an undeclared source reads as `User` and an `ai` prefix as `AI`, so a row never loses its provenance and a new source is a one-line addition. `GET /api/binaries/<id>/data-types` takes `?source=` (400 `invalid source` outside the four), always answers `sources` (the count per label over the whole model, so a filter cannot hide what it is hiding), and `reportal types <binary-id> --source LABEL` plus the `list_data_types` MCP tool expose the same. The SPA's Data types panel opens with a provenance strip whose counts are toggles, adds a Source filter, renders the list a page at a time with a Load more control, and keeps all four filters in the route hash so a filtered model is a link that survives a reload.
- Debug symbol ingestion: `reportal symbols <binary-id> <path>` (or `POST /api/binaries/<id>/symbols`, a multipart upload, or the binary detail's **Debug symbols** panel) stores a PDB or an ELF/DWARF file under `<workspace>/symbols/<sha256>` and parses it with stdlib readers: a DWARF subprogram, base type, pointer and struct member come out of `.debug_info` (DWARF 2 to 5, the indexed `strx`/`addrx` forms included), an ELF function and object table out of `.symtab`/`.dynsym`, and a PDB's public and procedure symbols out of the MSF container's DBI symbol record stream. The parse is applied as one journaled action: a function whose VA matches a symbol is renamed to it with the `symbol` name source and every aggregate type the file declares is created or updated in the editable type model, so a revert puts both back. `reportal symbols-status <binary-id> [--file-id N]` and `GET /api/binaries/<id>/symbols` read the ingests (404 `no-symbols` before the first), `reportal symbols-export <binary-id> [--format c|json] [--output PATH]` and `GET .../symbols/export` render one parse (the C form through the type model's own renderer, so the export and the model cannot disagree), and the `get_symbols`, `import_symbols` and `export_symbols` MCP tools expose the same. Each parse carries its `notes` naming what the reader did not do: DWARF location expressions and PDB types are not reconstructed, and names deeper than the type-depth cap are left out rather than guessed. A PDB writer is out of scope, so an export stays a C header or JSON, and a real
MSVC or lld PDB's addresses need its section header stream, which this reader does
not follow: a PDB symbol keeps its name and answers `va: null` rather than a
guessed address, so a PDB ingest records names in the parse and the export while a
DWARF one renames the functions it places.
- Agentic conversations: a plain turn answers one question over the stored context; an **agent run** works with tools. `reportal conversation-run <conversation-id> "<message>"` (or `POST /api/conversations/<id>/runs`) offers the model every tool the local MCP registry declares, runs the read-only ones it asks for through the same handlers the stdio server calls and feeds each result back as a tool turn, until it answers in text or the run reaches `agent.MAX_TOOL_CALLS`. A tool that changes the workspace is gated: the run pauses with the exact call it wants to make, `reportal conversation-confirm <id>` (or `POST .../confirm`, `Approve call`/`Reject call` in the SPA) approves or rejects it, and a rejection is fed back to the model as a refused call so the run continues instead of failing. `reportal conversation-runs`/`conversation-run-status`, `GET /api/conversations/<id>/runs[/<run_id>]` and the `list_conversation_runs`/`get_conversation_run` MCP tools read the runs; `reportal conversation-cancel` (or `POST .../cancel`) stops a live run at its next step boundary and refuses one that already finished (409 `run-not-cancellable`); and `GET /api/conversations/<id>/events` (or `reportal conversation-events`) streams the run's **state** as server-sent events, one frame per change, ending on a terminal status. The `run_conversation_agent`, `confirm_conversation_run` and `cancel_conversation_run` MCP tools expose the same over MCP. The run row and the messages a turn wrote are one journaled action, so a revert removes both; a tool the run called carries its own journal action, so reverting the conversation does not undo a tool's write. Retrieval, the store and the tools are all local; the only network call is the optional LLM bridge, and without an endpoint the route is 503 `llm-unavailable` and no run row is written.
- Function-level extras: `reportal indirect-calls <function-id>`, `function-capabilities <function-id>`, `function-strings <function-id>`, `user-string-add`/`user-string-rm`, `analysis-strings`/`analysis-strings-set`, `callee-add`/`callee-rm`, `callees-callers <function-id>...`, `canonical-names <function-id>... [--dry-run]` and `function-matches <function-id>...`, the `GET /api/functions/<id>/indirect-call-sites`, `GET /api/functions/<id>/capabilities`, `GET`/`POST`/`DELETE /api/functions/<id>/strings[...]`, `GET`/`POST`/`DELETE /api/functions/<id>/callees[...]`, `GET /api/functions/callees-callers?ids=`, `GET|POST /api/functions/matches` and `POST /api/functions/canonical-names` routes, the `GET`/`POST`/`PUT /api/analyses/<id>/strings` routes, the thirteen MCP tools from `get_indirect_call_sites` to `canonicalize_function_names`, and the function detail's panels plus the analysis log drawer's strings panel. Everything derived says so in its own `derivation` note: the indirect call sites come from the cached listing (a function with none reports `has_disassembly: false` rather than running the engine), the capabilities classify the function's own imports and literals through the same rule table the binary-level scan uses, the callees are the names its text mentions matched against the binary's function names, and a match read answers recorded rows and runs no scoring. The one thing that is not derived is an analyst-declared callee edge, stored with `source: analyst` and reported beside the derived names rather than merged; the analyst strings sit beside the literals the decompilation carries, never merged with them. `canonical-names` renames to a candidate the store already recorded and skips a function with none instead of renaming it to a guess, and every string and edge write is journaled.
- External sources: `reportal external-sources`, `reportal external <analysis-id> [--source NAME]` and `reportal external-status <analysis-id> [--source NAME]`, `GET /api/external/sources`, `POST`/`GET /api/analyses/<id>/external/<source>`, the `list_external_sources`, `get_external_report`, `get_external_status` and `run_external_source` MCP tools and the SPA's External view answer one question about one analysis. The offline `local` source derives its answer from the rows this workspace already holds (the fingerprint, the detected families, the capability tags, the threat report and the secrets count, each reported present or absent) and never makes a request, so the hosted feature has a meaning on an air-gapped install. The remote `virustotal` source is off until the workspace opts in (`REPORTAL_ALLOW_EXTERNAL` or `[external] allow_remote = true`) **and** a key resolves (`REPORTAL_VIRUSTOTAL_KEY`, then `[external] virustotal_api_key`, then the secret store's `virustotal.api_key`); a request goes to one fixed https host with the hash in the path, follows no redirect, is capped by `MAX_BYTES` and a timeout, and stores a normalized subset (per-engine results capped, no vendor links) rather than the whole response. A 404 is stored as `found: false`; any other failure answers 502 `external-fetch-failed` and stores nothing. A third party registers a source through the `reportal.external_sources` entry-point group.
- Secret store: `reportal secrets-set <name> [<value>] [--stdin] [--scope local|team] [--team-id N]`, `secrets-list` and `secrets-rm`, `GET`/`PUT`/`DELETE /api/secrets[/<name>]`, the `list_secrets`, `set_secret` and `delete_secret` MCP tools and the Secrets panel on the SPA's Users view hold named credentials at workspace or team scope. A read **never** returns the value: it reports the name, the scope, the team, the byte length and a last-four hint (and no hint at all for a value shorter than `secret_store.MIN_HINT_LENGTH`), so a screen share or a log cannot leak a key. The value is reachable only through `secret_store.value_of`, which an internal consumer calls on the caller's behalf: the optional AI bridge resolves its key from the environment, then `reportal.toml`, then the store under `llm.api_key`, and cluster H's external source will read the same way. A workspace secret needs an admin to write and a team secret that team's membership; with auth off the install is the single local operator. Every write is journaled, so a rotation is revertible and the previous value is what a revert restores. Values are local state in the workspace SQLite file, and [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) states the plaintext-at-rest boundary and the journal residual.
- Model registry and the analysis upgrade: `GET /api/models`, `reportal models` and the read-only `list_models` MCP tool name every model this install can produce a stored result with: the `rebrew` engine, each decompiler backend, the configured bridge model (or the single `unconfigured` entry) and the optional similarity extra, each with its kind, installed version, availability and the reason it is not. A third party registers one through the `reportal.models` entry-point group. An analysis records the model that last produced its artifacts (`analyses.model`, beside the per-artifact `ai_artifacts.model`), and `POST /api/analyses/<id>/upgrade` (`reportal analysis-upgrade <id> --model NAME [--function ID]... [--limit N]` and the destructive `upgrade_analysis_model` MCP tool) re-runs the analysis's stored LLM artifacts (summary, inline comments, type suggestions, identifier renames) under a named `llm` model, journaling every artifact it replaces so a revert puts the previous payloads back. A function whose re-run fails is reported in `skipped` and keeps its stored artifact; a model of another kind is 400 `invalid model`, an unknown name 404 `model not found` and an unconfigured bridge 503 `llm-unavailable`. The SPA's Models view tabulates the registry and carries the upgrade form. The hosted upgrade re-analyses the binary; reportal never does, and every response says so in its `note`.
- AI decompilation artifact: `reportal ai-decompile <function-id>` and `POST /api/functions/<id>/ai-decompilation` ask the configured endpoint for a complete rewritten function over the decompilation reportal already stored, and keep the whole artifact in one `ai_artifacts` row of kind `ai-decompilation` (so every write is journaled and revertible like the four flat artifacts). Beside the rewrite and the model it stores the placeholder token map, the per-line attributions, the analyst overrides, the rating and the per-line inline comments; `GET /api/functions/<id>/ai-decompilation` serves the rewrite rendered with its overrides, `.../status` the counts without the text, `.../events` the workflow as server-sent events, `.../tokens` the token map, `.../rating` and `.../inline-comments` the feedback, and `PATCH .../overrides`, `PATCH .../rating` and `POST`/`PATCH`/`DELETE .../inline-comments[/<line>]` write them. Three parts are local and deterministic rather than model-reported, and every response says so under `derivation`: the token map is a scan of the rewrite for the shapes the decompilers emit (`local_8`, `param_1`, `uVar2`, `DAT_...`, `FUN_...`), an attribution is a line diff against the decompilation the model read (`original`, `rewritten` or `added`, with the source lines each block paired with), and the served code applies the overrides at read time so clearing one restores the model's own words. `reportal ai-decompile`/`ai-decompilation`/`ai-decompilation-status`/`ai-tokens`/`ai-lines`/`ai-override`/`ai-rate`/`ai-line-comments`/`ai-line-comment-add`/`ai-line-comment-edit`/`ai-line-comment-rm`, the eleven MCP tools from `run_ai_decompilation` to `delete_ai_line_comment`, and the function detail's AI decompilation panel (lines with their origin, a per-token override input, the rating and a line comment editor) expose the same. A rewrite is one model call, so the event stream reports the state it finds rather than pretending to stream progress, and cancelling one in flight is not offered.
- AI decompilation pipeline: `reportal pipeline <function-id>` and `POST /api/functions/<id>/pipeline` run the portal's reported steps (preparing decompilation, reading the function trace, decompiling, searching for functionality, resolving names, naming variables and types, storing results) as a composition of components: each component declares what it requires and provides, the loader activates the ones whose requirements hold and records why the rest were skipped, and every persistent write is journaled with its inverse. The run is stored in `pipeline_runs`/`pipeline_steps` with each step's status, reason and duration; `GET /api/functions/<id>/pipeline` serves the latest run with the function's artifacts (404 `no-run` before the first run), a `[pipeline] disabled = [...]` table in `reportal.toml` skips stages, and `reportal pipeline-revert <run-id>` (or `POST /api/pipeline/runs/<id>/revert`) undoes exactly what the run wrote. Disassembly, decompilation, matches and the predicted name come from stored rows and the rebrew engine; the summary, inline comments and type suggestions come from the optional configured endpoint, and those stages are skipped with reason `llm-unavailable` without one. The function detail view renders the timeline, the predicted name with Apply rename, the summary, the comments and the decompilation, with a Revert run control. Components are hot-swappable at the registry level: `reportal components` lists the registry (name, requires, provides, origin, reloadable), `reportal components-reload <name>` (or `--all`, or `POST /api/components/reload`, or the SPA Components view) re-imports a component's declaring module and swaps the live entry, and `pipeline.ComponentHost` drives deactivate, reload and reactivate against one context. Withdrawal is exposed end to end: `reportal components-deactivate <name>` (or `POST /api/components/<name>/deactivate`, the `deactivate_components` MCP tool, or the Components view's per-row Withdraw control) runs the component's `revert` where it declares one, revokes the names it provided, and answers the `deactivated` entries plus a `journal_action` when the withdrawal recorded a durable write (a process-local binding records nothing and reports `journaled: false`). A reverted run reports the context bindings it changed under `context_changes`, each with whether the process applying the revert resolved it; a binding a later process cannot resolve is reported `applied: false`, never claimed as restored. A run already in flight keeps its snapshot, and a component registered in-process is not reloadable.
- Action journal: every wired mutating route and command records its inverse in a persisted `journal_entries` table, one action per request or invocation. `reportal journal [--action ID] [--limit N]` lists the entries newest first, `reportal journal-revert --action ID | --entry ID` replays them through the same undo dispatcher the pipeline and auto mode use, `GET /api/journal`, `GET /api/journal/<action>` and `POST /api/journal/revert` are the HTTP face, and the SPA Journal view lists the actions with a per-row revert. The wired set is binary upload and fingerprint, the binary and function bulk actions, tag creation, tag add and remove, function rename and history revert, the stored decompilation and match rebuilds, every scan that stores a `scans` row on the routes, the CLI and the MCP tools (plus the `analyses` carrier when the action created it), knowledge ingest (file, pasted text and URL) and document delete, comment create, update and delete, conversation create, delete and message send, analysis and collection creation, collection add, family registration and deletion, the editable data-type and signature models and their exported headers, the AI artifacts, the graph rebuild and the PDF report file.  Those entry points add a `journal_action` field to their response when they recorded a write, a destructive MCP tool carries the same field in its payload, and a revert works from another process because the descriptors are stored. A revert removing a conversation exchange does not undo the model call that produced it, and a graph rebuild's revert restores the local rows only. See `docs/COMPONENTS.md` for what is still unwired and why.
- Auto-mode orchestration: `reportal auto <binary-id> [--worker offline|llm_c_source] [--execute] [--concurrency N] [--functions-per-task N] [--max-attempts N] [--max-tasks N] [--recover]` decomposes the binary's not-yet-matched functions into a task tree (one root, one batch per group) and works the batches on bounded worker threads, aggregating verified results bottom-up into a coverage delta (`matched`/`improved`/`failed`/`skipped`, `coverage_before` to `coverage_after`). The shape follows the sibling `spydr` project, and acceptance is objective: a function counts as matched only when its worker carries a matching status from `rebrew test`, so an unverified claim is downgraded. The default is a **dry run**: nothing is compiled, no source file is written into the rebrew project and no function status changes. `--execute` (or `"execute": true` on the API) writes the candidate into the project's reversed source directory and compiles it, never overwriting an existing file, and records every file it wrote and every status it replaced, folding each completed batch's descriptors into the run's undo plan in the same commit as its result, so a hard kill loses at most the batch in flight; `reportal auto-revert <run-id>` puts the recorded files and statuses back. A run a dead process left `running` is closed by `reportal auto-recover <run-id>` (or `--recover`, which recovers the binary's latest stale run before starting): it marks each unfinished task `failed` with reason `interrupted`, merges what those tasks had recorded into the undo plan and closes the run `failed`, `partial` or `done`. `POST /api/binaries/<id>/auto` answers 202 with the run id and works it in a background thread; `GET /api/binaries/<id>/auto` (404 `no-run`) and `GET /api/auto/runs/<id>` serve the live task tree, `POST /api/auto/runs/<id>/recover` closes a stale run, and the SPA Auto-mode view renders the tree with a start form and a revert control. The built-in `offline` worker is deterministic and needs no LLM or engine; `llm_c_source` asks the configured endpoint for an MSVC6/C89 source file in rebrew's annotation format and verifies it with `rebrew test --json`. Workers are plugins, in the same shape as components (the `reportal.auto_workers` entry-point group).
- Function rename with full history and revert (`reportal revert`), plus apply-match (`reportal apply-match`); collections; binary tags (`reportal tags`, `reportal tag <binary-id> <name> [--remove]`); a typed cross-entity search. `GET /api/search?q=&kind=&limit=` searches binaries, functions, collections and tags; `kind=all` (the default) is the substring search, and `kind=sha256` matches a full hash or a prefix long enough to be unambiguous, `kind=binary` a binary name, `kind=collection` a collection name and `kind=tag` a tag name. Rows carry the stored metadata (size, format, arch, created, tags, member counts) and the field that matched, `counts` reports each group's returned count against its matched total, and an ambiguous or malformed hash prefix answers 400 `short-hash`/`ambiguous-hash`/`invalid-hash`. The SPA Search view renders the grouped tables and the `⌘K`/`Ctrl+K` modal searches from anywhere.
- Analyst comments: `reportal comments --binary ID` (or `--function ID`) lists the comments stored on a binary or function, `reportal comment-add --binary ID "text" [--author NAME]` stores one and `reportal comment-rm <comment-id>` deletes one. `GET`/`POST /api/binaries/<id>/comments` and `GET`/`POST /api/functions/<id>/comments` list and add, and `PATCH`/`DELETE /api/comments/<id>` edit and delete. A scope must exist and a body is trimmed and capped at `comments.MAX_COMMENT_CHARS` (400 `invalid comment` for a blank or oversized body); the author defaults to `comments.DEFAULT_AUTHOR`. The SPA carries a Comments panel on both detail views with per-comment edit and delete for the browser's own author, and the Binaries list shows each binary's comment count. This is separate from the AI inline-comments artifact, which is served at `/api/functions/<id>/ai-comments`.
- Bulk actions: `POST /api/binaries/bulk` applies `add_tag`, `remove_tag` or `delete` to a bounded id list and `POST /api/functions/bulk` applies `rename` (prefix) or `clear_matches`; both answer `{"action", "requested", "applied", "skipped": [{"id", "reason"}]}` and skip an unknown id with a reason instead of failing the batch, with a `MAX_BULK_IDS` cap and a named action set. `reportal bulk-tag <tag> <binary-id>... [--remove]`, `reportal bulk-delete <binary-id>... [--yes]` (a confirmation is required without `--yes`) and `reportal bulk-prefix <prefix> <function-id>... [--replace]` wrap them, and a prefix rename records every change in `name_history` with source `bulk-prefix`. The SPA Binaries list carries selection checkboxes with the tag and delete bar, and the Functions list a bulk prefix rename.
- Knowledge documents and search: `reportal ingest <binary-id> <path>` chunks and stores a text file in a binary's scope, `reportal documents <binary-id>` lists them and `reportal knowledge <binary-id> "query"` ranks their chunks; `POST /api/binaries/<id>/documents` (upload), `POST /api/documents` (pasted text), `GET`/`DELETE /api/documents/<id>` and `GET /api/knowledge/search` expose the same store, and the SPA Knowledge view lists, ingests and searches. Ranking uses an embeddings endpoint when one is configured and a local TF-IDF cosine otherwise, so it works with zero configuration. Guarded remote ingestion is off by default and adds `reportal ingest-url <binary-id> <url> [--title TEXT] [--project]`, `POST /api/knowledge/fetch`, `GET /api/knowledge/config`, the SPA URL field (shown only when the server reports it enabled) and the destructive `ingest_url` MCP tool, with the SSRF guards in `remote_ingest.validate_target`. Retrieval is read-only: `reportal context <function-id> [--query TEXT]`, `GET /api/functions/<id>/knowledge` and `GET /api/binaries/<id>/knowledge` return the best matches, the `retrieve_knowledge` MCP tool exposes the same, and the retrieved text grounds conversations (returned as `sources`) and the AI decompilation pipeline, always quoted as untrusted context.
- Knowledge graph: `reportal graph-build <binary-id>` derives a deterministic entity/relation graph from the stored rows (the binary, its functions, the recorded matches, its documents, the stored struct/capability/unstrip/triage scans and its tags) and `reportal graph <binary-id> [--node ID]` prints the node counts by kind or one node's neighbors grouped by relation. `POST /api/binaries/<id>/graph`, `GET /api/binaries/<id>/graph` (404 `no-graph` before the first build, `?kind=`, `?include_documents=true`) and `GET /api/graph/nodes/<node_id>` expose the same calls, the SPA Graph view renders the counts, a filterable node table and the neighbor groups, and `get_graph`, `graph_neighbors` and `build_graph` are the MCP tools. Call edges are omitted when the store does not carry them, and the build involves no LLM, no engine run and no new dependency. The graph is pluggable: `reportal graph-backends` lists the registered backends, `reportal graph-sync <binary-id> [--backend NAME]` pushes a binary's graph to one (the built-in `sqlite` backend reports the local counts without copying anything, and the optional `cognee` backend pushes it into a Cognee dataset when the `cognee` extra is installed), and `reportal graph-query <query> [--backend NAME]` searches a backend that supports querying. `GET /api/graph/backends`, `POST /api/binaries/<id>/graph/sync` and `GET /api/graph/query?q=&backend=` are the HTTP face, `list_graph_backends` and `sync_graph_backend` the MCP tools, and the SPA Graph view carries the backend selector, the Sync control (disabled with its reason when the backend is unavailable) and the query box. A backend that is not installed answers 503 `backend-unavailable` with the install hint, and a third party adds one through the `reportal.graph_backends` entry-point group.
- Plugin-seam inventory: `reportal integrations` (or `GET /api/integrations`, the read-only `list_integrations` MCP tool, or the SPA Integrations view) reads the five registries reportal loads plugins through (pipeline components, auto-mode workers, graph backends, effect handlers, MCP tools) and reports each seam's entry-point group with one row per part it currently holds, so what this process actually loaded is never guessed at.

- Analysis lifecycle and log: an analysis carries a status from the closed set `store.ANALYSIS_STATUSES` (`pending`, `processing`, `done`, `failed`, `cancelled`, mapping onto the hosted portal's Queued, Processing, Complete and Error). The writers advance it honestly rather than leaving a scan's outcome implicit: creating one records the creation, `store.set_scan` marks the analysis `done` and logs the scan's finish, and `store.scan_span` (wired into the scan helpers the routes already call) logs a scan's start and marks the analysis `failed` with an error entry when the wrapped engine work raises, so an analysis with a failed scan is never silently complete. Every event lands in `analysis_log_entries` through `analysis_log.append_entry`, with a severity from `analysis_log.SEVERITIES` (`info`, `warn`, `error`), the message and the time; `GET /api/analyses/<id>/logs` (and `reportal analysis-logs <analysis-id>`) reads them newest first, bounded, with the log's true total. `GET /api/analyses` takes `status`, `search`, `order` and `limit` filters, `DELETE /api/analyses/<id>` (and `reportal analysis-delete <analysis-id>`) removes an analysis with its functions, matches, scans and log through the journal, refused 409 `last-analysis` for a binary's only analysis while it holds functions, and `reportal analyses [--status S] [--search TEXT] [--order newest|oldest] [--limit N]` lists them with their binary, status, size and tags. A requeue route is deliberately not built: the stored scans hold results, not the inputs they ran with, so a re-run cannot be reconstructed and a route would only reset a status with nothing behind it (see `docs/PARITY.md`).

Not built yet (see `docs/PARITY.md` for the full map):

- The full DIE signature database (the engine's own toolchain detection still uses an external `diec` when it is installed; the bundled detection is the curated `filetypes.SIGNATURES` table over data reportal already fetches).
- The hosted portal's own AI models and its AI `crypto-explain` narrative and model-driven threat report (the local Threat report is deterministic IOC/ATT&CK output with an optional LLM summary, and its software type and threat score are reportal's own evidence-based heuristics, not a model score); the hosted security/LM agents.
- Snort and STIX outputs are a basic content rule and a minimal deterministic 2.1 bundle, neither schema-validated against an external validator.
- Auth is unbuilt.

Sandbox detonation is off by default: reportal runs nothing until the workspace
opts in (`REPORTAL_SANDBOX=enabled` or `[sandbox] enabled = true`) and a runner
such as bubblewrap is installed, and when it does run a sample it does so with no
network, a read-only root, one writable directory, capped memory and CPU and a
wall-clock timeout, recording the report. Static PE/ELF analysis needs no
unpacking. See `docs/PARITY.md` for the full map and `docs/THREAT_MODEL.md` for
what the sandbox does and does not promise.

## Development

`make check` is the whole gate: ruff and ruff format, oxlint, shellcheck, W3C
VNU over the HTML and CSS, mypy (the flag set in `pyproject.toml`), `tsc
--noEmit`, pytest under the coverage floor, the built SPA smoke and audit in
headless Chrome, and the wheel packaging check. `make check-fast` drops the
slow parts (the coverage trace, and the browser and wheel targets) for
iteration.

```bash
uv venv .venv
uv pip install -e ".[dev]" --python .venv/bin/python
cd web && bun install
make run            # build the SPA and serve the portal (PORT=8002)
make check          # the whole gate
make check-fast     # no coverage, no browsers, no wheel
```

Individual targets: `make run` (build the SPA, then serve) and `make serve`
(serve the current build, no rebuild), `make lint`, `make typecheck`, `make
test` (with coverage), `make test-fast`, `make ui` (build the SPA, then the
smoke and audit), `make package-check`. `shellcheck` and `vnu` are the two
external tools the lint step requires, and `vnu` needs Java 17+.
